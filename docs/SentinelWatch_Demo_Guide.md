# SentinelWatch: ten-minute demonstration

This guide was walked against the real UI at `http://127.0.0.1:8000` using read-only navigation. Open with **Wayanad**, the clearest visual incident. The server is already running from the first-run snapshot: **do not restart it, run checks/replays or change its data during preparation or the read-only demo**. The times below are presentation allocations, not measured software runtimes.

## Prepare the saved evidence

- Open [Wayanad archive incident](http://127.0.0.1:8000/#/case/4f26f148-c1f2-422d-901f-419e71688f1b), [Jewar archive incident](http://127.0.0.1:8000/#/case/78bb17c0-26d3-4a1e-b2cb-8673f62e2b55), [Rawa archive incident](http://127.0.0.1:8000/#/case/ac5baeb8-b7d3-4966-a422-8f763e4cbda6) and [Kanha site](http://127.0.0.1:8000/#/site/9c7ed254-482d-4da3-9e55-662367272aac) in tabs. The IDs belong to the shipped snapshot.
- Prepare [Operations](http://127.0.0.1:8000/#/), [Alerts](http://127.0.0.1:8000/#/alerts), [Departments](http://127.0.0.1:8000/#/departments), [Zones](http://127.0.0.1:8000/#/zones) and [Models and data](http://127.0.0.1:8000/#/models).
- Keep the [final project PDF](../output/pdf/SentinelWatch_Final_Year_Project_Report.pdf) and [real screenshots](screenshots/README.md) available locally. A **case investigation PDF** is a separate artifact, downloaded through **Download PDF report** on an incident. The documentation walk did not click that button; prior valid downloads are recorded in `offline_ui_proof` and `restore_proof`.
- Check projector readability. Dynamic “ago”, scheduler countdown and latest catalogued scene labels change with time; do not memorise them as fixed results. The header's **Live** means the update connection, while the incident's **Archive replay** identifies historical processing.
- Do not click **Check now**, **Start replay**, **Pause**, **Resume**, **Acknowledge**, **Send to field verification**, **Resolve**, **Mark false positive**, **Dispatch again**, **Remove site**, **Add zone** or a delete icon. Read their purpose aloud without recording a fictitious field action.

## Recovery plan

| Failure | Read-only recovery | What to say |
|---|---|---|
| Venue Wi-Fi fails | Keep the server running and open a saved local incident. Use the inspected report/screenshots if needed. Do not start a replay. | “These are already processed real observations. The recorded offline browser proof loaded comparison layers, moved the slider and downloaded a valid case PDF with external requests blocked. New catalogue searches and uncached pixels still need network.” |
| Imagery provider fails | Read the recorded error and move to saved evidence. Do not keep clicking Check now. | “Per-band retry, failover and a hard imagery-fetch deadline limit waiting; they do not guarantee provider availability.” |
| Clouded / no new scene | Show **Status**, **Scene timeline** and saved **Findings history**. | “The newest catalogued scene may be unusable; it is not necessarily the last analysed scene. The app does not invent an observation.” |
| Replay slow or blocked | Use the existing badged replay. Leave the running demo untouched. | “A new replay requires catalogue access; completed replay evidence is independent of a new request.” |
| Projector too narrow | Use the prepared deep links, modest browser zoom and one evidence panel at a time. | Keep acquisition dates, origin and verdict readable. |
| Browser loses connection | Reload the local page once; preserve the existing server/database. If the server has actually failed, the demo owner may restart the same launch command against the same storage. This task did not stop or restart it. | “Saved evidence persists. A restart is different from deleting and restoring the snapshot.” |
| Model unavailable | Show actual method/status; use the saved case with its original provenance. | “A spectral fallback is labelled. It is not a new neural-model result.” |
| SMTP absent or failed | Show **Delivered to inbox** and the separate email outcome. | “Routing is recorded; this email was not sent. SENT would mean server acceptance, not officer receipt.” |
| Case PDF unavailable | Show on-screen evidence and the inspected final project PDF. | “A case download and the project report are separate. A failed download is not a successful fresh report.” |

## Return to the clean snapshot after a separate rehearsal

**Do not perform this on the running exam demo today.** Repeated replays add replay alerts because each new replay has its own identity. To deliberately discard local rehearsal data later, stop the server, delete `instance/sentinelwatch.db*` (including WAL/SHM sidecars), `storage/outputs` and `storage/outbox`, then restart with the normal launch command. This is a destructive reset of local cases/reviews/alerts, not routine failure recovery; retain any evidence you need first.

This wording was checked against `app/snapshot.py`: `restore_snapshot_if_empty()` checks that monitoring areas and cases are empty, then imports rows from `demo_snapshot/` and copies its JPEG outputs. It runs only when snapshot restoration is enabled and the snapshot manifest/database are present. With the default database/storage paths and the shipped snapshot, restarting after that deletion restores the snapshot. Custom paths must be reset at their configured locations instead. The reset itself was **not executed** by this documentation task. Raw imagery caches and outbox bodies are not part of the snapshot; retained delivery history does not promise downloadable email files.
